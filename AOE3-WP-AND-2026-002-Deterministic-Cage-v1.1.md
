1. Abstract

Android was engineered around applications whose control-flow graphs are authored before compilation and whose privilege boundaries are declared statically in `AndroidManifest.xml`. Autonomous AI agents invalidate that model: they synthesize tool calls, file mutations, inter-process calls, and outbound network requests dynamically at runtime from untrusted natural-language inputs. When a single agent process holds high-leverage Android capabilities, untrusted text arriving through a message, document, or web response can steer privileged system interactions without any change to the underlying APK bytes.

Existing platform defenses such as Google Play Protect operate primarily as global, reputation-driven admission and heuristic screening mechanisms; they answer a reputation question ("Is this binary known or inferred to be risky across the ecosystem?") rather than a local, deterministic policy question ("Does this specific runtime action comply with the device owner's explicit rules right now?").

In this paper, I propose the AOE3 (Agent Operating Engine) Deterministic Cage Model and open specification to govern AI agents on Android across five architectural components: a Cage Policy Kernel, a Watcher Verifier in a separate UID, a Ruling Layer backed by owner-signed cryptographic approvals, an append-only hash-chained Ledger, and a Soul/User Boundary File bound to agent identity. I ground the problem statement in an observed baseline recorded in my evidence register as Case 0 (Section 3), without claiming deployment, standardization, or adoption by any platform vendor.

2. Broken Assumptions of Legacy Android Security

Android enforces application isolation through per-package Linux user IDs (UIDs), SELinux policy domains (such as `untrusted_app` and `priv_app`), cryptographic APK signing schemes (v2/v3/v4), and runtime permission prompts (`checkSelfPermission` / `AppOpsManager`). Those primitives assume that an application's behavior aligns with its declared purpose and that human consent precedes distinct actions. Autonomous agents break three foundational assumptions of that design.

2.1 User-Reads-Before-Granting Fails Under Standing Ambient Authority

Traditional permission prompts map to discrete, human-initiated features: tapping a shutter button invokes `CAMERA`, or selecting a contact invokes `READ_CONTACTS`. An autonomous agent, by contrast, requires standing, ambient authority across tasks and time to operate unattended or multi-step. To observe context, maintain continuity, and act across applications, an agent routinely requests `AccessibilityService` (`BIND_ACCESSIBILITY_SERVICE`), `QUERY_ALL_PACKAGES`, `MANAGE_EXTERNAL_STORAGE`, or foreground-service execution exemptions (`FOREGROUND_SERVICE_SPECIAL_USE` / `FOREGROUND_SERVICE_DATA_SYNC`).

Once granted, these capabilities persist across sessions without re-prompting for each downstream consequence. A human user cannot predict at setup time what screen content an `AccessibilityService` will read three days later or which external endpoint an agent will call after parsing an incoming email. Consent given once at installation or configuration becomes broad ambient delegation over future, unknown runtime states.

2.2 Install-Time and Reputation Scanning Fails When Payload Arrives as Prompt Text

Static bytecode inspection, manifest auditing, native library checks, and reputation scoring evaluate an application artifact and its lineage prior to or at installation. An agentic application can ship with completely benign DEX bytecode, standard HTTP client libraries, and clean cryptographic signatures. Its runtime behavior is driven by model inference over external text — prompts embedded in chat messages, calendar invites, HTML pages, attachments, or tool outputs.

Because the adversarial instruction does not exist inside the APK at install time, a binary can pass install-time screening as a clean API client and later be steered via prompt injection to read sensitive local files, summarize confidential records, or transmit data over an allowed network channel. Install-time verdicts cannot evaluate semantic instructions synthesized mid-session from untrusted data streams.

2.3 UID and SELinux Sandbox Isolation Fails Above the Process Boundary

Android's Linux UID separation and SELinux type enforcement prevent one `untrusted_app` process from directly reading another app's private data directory (`/data/data/<package>`) or accessing restricted kernel interfaces without explicit policy rules. That isolation protects processes from unauthorized cross-UID memory and file access, but it does not govern an agent that is explicitly authorized to act as an intermediary or to use its own accessible resources in harmful ways.

First, an agent granted `AccessibilityService` or `NotificationListenerService` operates above individual application sandboxes by observing rendered UI hierarchies (`AccessibilityNodeInfo`), notifications, and input events across apps, and by dispatching synthetic UI actions (`performAction`). Second, even strictly within its own UID and scoped storage view, an agent holding OAuth tokens, local caches, or user-shared files can be induced by prompt injection to exfiltrate data it legitimately holds to an external destination. The sandbox isolates processes and kernel resources; it does not constrain agent capability selection or external-effect execution.

3. Case 0: Observed Baseline in Sealed-Device Custody

On 2026-11-23, on my Huawei P30 lite running EMUI 12.0.0 with an Android security patch level of May 1, 2022 (unpatched for more than four years), Google Play Protect blocked installation of a sideloaded agent APK ("Kimi Claw") at the install stage. The verbatim warning displayed on screen was:

> "This app can request access to sensitive data. This can increase the risk of identity theft or financial fraud."

I preserve this event as Case 0 in my evidence register, with the device state snapshotted and held in sealed-device custody. From this single observation, I separate direct observations from architectural inferences across three points:

1. Server-side verification without OEM patch currency. Observation: The device remained on the May 1, 2022 security patch level while Google Play Protect executed its pre-install evaluation and returned a block verdict. Inference: Cloud-assisted verification delivered through Google Mobile Services can enforce application-boundary gating on legacy devices whose vendor OS security patches have long lapsed.
2. Opaque verdict and absence of owner-authored policy. Observation: The prompt reported that installation was blocked and stated generic risks ("identity theft or financial fraud"), without surfacing which rule, permission, or signal triggered the decision, and offered no interface to write a custom rule. Inference: Binary install blockers provide low diagnostic transparency for technical owners and cannot express fine-grained, owner-defined runtime constraints (such as permitting local execution while restricting network egress or file paths).
3. Probabilistic reputation and un-caged post-install runtime. Observation: The block occurred at install time based on a risk warning rather than a deterministic policy proof tied to runtime actions. Inference: Reputation-based admission is probabilistic — repackaging or re-signing the same agent APK can alter how reputation signals apply — and install-time gating alone leaves post-install runtime actions uncaged.

4. The AOE3 Security Doctrine

To govern autonomous agents without relying on probabilistic model self-restraint, AOE3 enforces five architectural invariants:

1. Non-equivalence axioms: Trusted != Verified; Installed != Authorized; Intent != Capability. Security claims are recomputed from bytes, never inherited from reputation. No component may treat a signed APK, a prior install state, a clean reputation score, or a persuasive model rationale as proof of present authorization.
2. "Machines draft and verify; rulings belong to the human." No external-effect action is final without a signed, timestamped, revocable, logged owner ruling bound to the hash of the exact proposed action. Agents and automated verifiers prepare structured proposals and check preconditions; authority over outward state changes remains human.
3. Every watcher is itself watched: AOE3 maintains an append-only hash-chained ledger in which the owner holds the root verification keys, so that any sequence gap, missing entry, or broken hash link is cryptographically detectable. A security monitor without auditability over its own continuity becomes an unverified authority.
4. Deterministic Cages: Agent behavior is bounded by a declarative, machine-verifiable policy over filesystem paths, Binder/API classes, and network egress. "The model talks; the cage decides." Safety prompts govern intent; the cage governs capability.
5. SMiCE alignment (Human vs. AI): The cage is the SMiCE principle — machines draft and verify, the human rules — made mechanical.

5.1 Five Core Components

1. Cage Policy Kernel

The Cage Policy Kernel executes in its own dedicated Android UID (`cage_uid`) and acts as the runtime capability gatekeeper for caged agents. Rather than granting the agent direct network sockets or broad filesystem/IPC access, the kernel enforces a declarative policy profile specifying allowed path prefixes, allowed Binder/API classes and target components, and allowed network egress endpoints.

In Phase 1, egress mediation uses `VpnService.Builder.addAllowedApplication(agent)` paired with an `onRevoke()` / `NetworkCallback` watchdog that immediately suspends the agent session and revokes ephemeral tokens on TUN loss; in Phase 2, `setAlwaysOnVpnPackage(lockdownEnabled=true)` locks routing to the cage path. Kernel-level zero-socket enforcement (AID_INET / SELinux neverallow) is Phase 4 only, and loopback or AF_UNIX traffic is not intercepted by `VpnService`. Outbound traffic routed through the cage is evaluated against explicit destination/port/SNI/protocol rules before any upstream socket is opened. For storage access, the kernel mediates file descriptors via `DocumentsContract` / Storage Access Framework (SAF) URIs or scoped workspace brokers rather than handing out raw directory paths, returning deterministic denial (`EACCES` or equivalent IPC refusal) on any out-of-policy request.

2. Watcher Verifier

The Watcher Verifier runs in a separate UID (`watcher_uid`) isolated from both the agent UID and `cage_uid`. Before an agent session starts, it computes SHA-256 digests over the base APK, any split APKs, dynamically loaded DEX or native code artifacts, the Soul/User Boundary File, and the active policy manifest — recomputing digests from bytes rather than trusting cached metadata (Section 4.1).

The agent wrapper prohibits dynamic code loading (`DexClassLoader`, `InMemoryDexClassLoader`, or `dlopen` on writable paths), or else requires pre-declared SHA-256 digests of any secondary DEX or `.so` artifact in the signed Soul/User Boundary File, loaded via a Watcher-verified file descriptor. During execution, the Watcher Verifier inspects proposed action parameters for structural abuse before they reach the Cage Policy Kernel or Ruling Layer: directory traversal sequences (`..`), anomalous path normalization, open redirects or host mismatches in URLs, and high-entropy or encoded payloads (such as Base64/hex blobs) embedded in outbound parameters that resemble covert exfiltration. It emits periodic signed heartbeats to the Ledger; if the Watcher misses a heartbeat window, fails self-check, or encounters a runtime fault, the system halts the agent session, revokes ephemeral session grants, and records a `WATCHER_FAULT` entry.

3. Ruling Layer

When an action crosses an external-effect boundary — such as transmitting data outside the device, sending an external message, altering external state, or requesting an action not pre-cleared by policy — execution pauses pending human authority (Section 4.2). The Ruling Layer constructs a canonical CBOR/COSE action digest binding the target identifier, payload SHA-256 hash, expiration timestamp (TTL), and a unique nonce.

It presents the exact structured fields — never unverified prose generated by the agent — inside a system-owned UI surface protected with `FLAG_SECURE`, `setFilterTouchesWhenObscured(true)`, and `setHideOverlayWindows(true)` (API 31+). The Ruling Layer refuses to render while an untrusted `AccessibilityService` is active, and `BiometricPrompt` renders in SystemUI outside third-party node trees. Approval uses `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG)` for per-use `CryptoObject` signing with a Keystore/StrongBox non-exportable key, while any device-credential fallback uses a separate bounded-TTL session key rather than a per-action StrongBox key. The resulting signature is recorded alongside a local revocation table so standing or active rulings can be revoked before expiry. Unsigned, malformed, replayed, or expired rulings are rejected and result in denial.

4. Append-Only Hash-Chained Ledger

The Ledger records security-relevant state transitions in an append-only sequence: policy loads, Watcher verification results, Cage allow/deny decisions, Ruling Layer prompts/approvals/denials/revocations, and Watcher heartbeats or faults (Section 4.3). Each record contains a monotonic sequence number (seq), UTC timestamp, emitting component ID, canonical event payload, the cryptographic hash of the preceding entry (prev_hash), and a signature or MAC keyed under the owner's verification key hierarchy.

Hash-chaining provides tamper-evidence (detecting modification, deletion, or truncation), not tamper-prevention against local compromise; the Ledger is exportable for external inspection and anchors the chain tip (seq, H_n) via an offline or remote append-only witness. If an adversary or faulty process truncates entries, alters a payload, skips a sequence number, or breaks the hash chain, verification detects the discontinuity immediately and places the cage into lockdown.

5. Soul / User Boundary File

The Soul / User Boundary File is an owner-signed manifest bound cryptographically to the target agent's APK hash and signing certificate digest. It declares the agent's permitted identity, operational mandate, and hard prohibitions (actions that are unconditionally forbidden regardless of prompt context or conversation history).

The Watcher Verifier validates the signature and identity binding at boot before the agent is allowed to run. If the signature is invalid, the APK hash or certificate digest does not match, or the file is missing or tampered with, the agent remains inert with no active capability grants.

7. Positioning

AOE3 is designed to be complementary to Google Play Protect and Android platform defenses, not a replacement for them. Play Protect addresses a global reputation question across the ecosystem — whether a binary or publisher aligns with known risk signals and fleet telemetry. AOE3 addresses a local deterministic policy question on a specific device — whether a verified agent process is allowed to perform a specific path, Binder/API, or egress operation under the owner's rules and cryptographic rulings.

The cage model should be an open standard, owner-policy-driven, verifiable by recomputation; watchers rank on evidence, never on vendor mood. When policy rules, digests, signatures, and hash chains are open and recomputable from bytes, security claims do not depend on opaque scores or shifting vendor posture. My strategic read is straightforward: platform watchers validating the cage thesis is market proof the problem is industry-wide.

8. Verification Discipline

Any reference implementation of the AOE3 Deterministic Cage Model is governed by three invariants:

1. Deterministic reproducibility of verdicts: Given identical policy manifests, Soul/User Boundary Files, artifact digests, and input events, the cage is designed to produce consistent allow, deny, or ruling-required verdicts across test runs. I state this as a design goal and test criterion — never as a guaranteed property of unbuilt software.
2. Fail-closed default: Any missing signature, expired or revoked ruling, malformed schema, unverified artifact hash, or ambiguous policy state resolves to denial (`EACCES` / non-execution) rather than silent allowance.
3. Zero silent overrides for external-effect actions: No automated retry, heuristic bypass, or unlogged fallback may finalize an external-effect action without a valid, owner-signed ruling recorded in the Ledger.

9. Roadmap

The following four phases outline how I intend to advance AOE3 from specification to implementation:

1. User-space PoC with loopback cage on unmodified Android: Build a prototype separating `watcher_uid`, `cage_uid`, and agent UID on standard Android devices using a local `VpnService` loopback proxy, scoped/SAF mediation, Keystore/BiometricPrompt signing, and a hash-chained Ledger. Exit criterion: All five scenarios in Section 6 are tested end-to-end with Ledger entries and denial/approval traces captured on target devices.
2. Android Enterprise work-profile enforcement with attestation: Extend deployment into an Android Enterprise work profile using `DevicePolicyManager` controls and hardware-backed Keystore/StrongBox key attestation to harden policy persistence and agent isolation. Exit criterion: Attested key and policy enforcement tests pass on devices supporting hardware-backed attestation, with bypass attempts logged as denials.
3. Open specification with CDDL schemas and deterministic compliance suite: Publish the AOE3 policy grammar, Soul/User Boundary File format, Ruling Layer COSE/CBOR structures, and Ledger chain rules using CDDL schemas alongside a deterministic test vector suite. Exit criterion: A reference verifier validates compliance test vectors covering valid rulings, expired/revoked rulings, policy denials, and broken hash chains.
4. Long-term AOSP Binder/SELinux integration: Propose native AOSP hooks integrating cage capability checks with Binder IPC and SELinux domains to reduce user-space proxying overhead. Exit criterion: A working AOSP prototype branch boots cleanly and demonstrates policy enforcement across Binder and network boundaries under test suites.

All milestones above are targets and design criteria for a proposed architecture, not deployed products or guaranteed outcomes.
